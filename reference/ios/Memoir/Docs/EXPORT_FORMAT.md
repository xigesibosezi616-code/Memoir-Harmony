# 尺素备份包（.memoir）格式与实施方案 · v1.0

> **状态**：**iOS 端导出 + 导入已实现并验收**（2026-08-06）。formatVersion = 1 已冻结，
> 鸿蒙端可以按本文档开工；**任何一方改格式必须同步改本文档并升 `formatVersion`**。
> 决策记录见 §5。
> **目的**：把一个用户的全部日记打成单个文件，可经微信/隔空投送/文件 App 传给自己，
> 在**任意一台装了尺素的设备**（新 iPhone、鸿蒙手机）上原样恢复。
> **与 CloudKit 的关系**：互补，不是二选一。见 §1。

---

## 1. 为什么两个都要做

| | CloudKit 同步 | 备份包导出 |
|---|---|---|
| 触发 | 自动、持续、无感 | 用户主动 |
| 范围 | 同一 Apple ID 的设备之间 | **任意设备，含鸿蒙** |
| 断网/换生态 | 不可用 | 可用 |
| 用户能拿在手里 | 否 | **是**（可自行归档） |

**关键点：鸿蒙端没有 CloudKit。** 用户从 iPhone 换到华为，或想同时用两台，备份包是**唯一**的数据通路。
所以它不是"锦上添花的导出功能"，是双端战略的必要组件。

## 2. 文件格式

### 2.1 容器

标准 **ZIP**，扩展名 `.memoir`。

选 zip 不选自定义二进制：鸿蒙（ArkTS）、Android、桌面端都能零成本读；用户好奇时改名成 `.zip`
就能解开看见自己的东西 —— 对一款主打私密和信任的产品，**数据可被用户自己检视**本身就是承诺的一部分。

```
尺素备份_20260805.memoir
├── manifest.json          # 版本、导出信息、校验
├── entries.json           # 日记
├── letters.json           # 笔友来信
├── taxonomy.json          # 标签 + 心情定义
└── media/
    ├── photo_a1b2c3d4.jpg
    ├── photo_a1b2c3d4.mov   # Live Photo 的视频部分
    └── audio_20260805_1.m4a
```

### 2.2 manifest.json

```jsonc
{
  "formatVersion": 1,          // 结构版本，破坏性变更才 +1
  "app": "memoir",
  "appVersion": "1.0.0",
  "platform": "ios",           // ios | harmony
  "exportedAt": "2026-08-05T12:00:00Z",
  "counts": { "entries": 128, "letters": 14, "media": 96 },
  "includesMedia": true,       // 「仅文字」导出时为 false
  "mediaTotalBytes": 184320000,
  "encrypted": false           // 明文标记，让读取方在解密前就知道要不要问密码
}
```

**写入方请把这些字段都写全**；但读取方**不要因为缺字段就整包拒收** ——
iOS 端的实现除 `formatVersion` 外全部有缺省值兜底（缺 `encrypted` 按 false、缺 `counts` 按 0），
理由见 §2.4 规则 3 的精神：宁可信息残缺，也不要用户的备份打不开。

### 2.3 entries.json

```jsonc
{
  "entries": [
    {
      "id": "8B1F...UUID",      // 合并去重的依据
      "title": "搬进新公寓的第一天",
      "date": "2026-06-24T10:30:00Z",
      "createdAt": "...", "updatedAt": "...",
      "mood": "calm",
      "moodColorHex": "#A8C5B8",
      "tags": ["生活", "搬家"],
      "isFavorite": false,
      "weatherCode": "rain",
      "weatherInfo": "26°",
      "locationInfo": "广州市",
      "audio": ["audio_20260805_1.m4a"],   // 指向 media/ 内的文件名
      "blocks": [                           // 与 ContentBlock 一一对应
        { "type": "text",  "text": "今天终于搬进了新公寓……" },
        { "type": "photo", "file": "photo_a1b2c3d4.jpg",
          "liveVideo": "photo_a1b2c3d4.mov",
          "liveStill": "photo_a1b2c3d4_full.jpg",
          "paperStyle": "polaroid", "position": "right",
          "rotationAngle": -1.4, "isCover": true }
      ]
    }
  ]
}
```

**媒体一律用文件名引用，不内嵌 base64。** 内嵌会让 JSON 膨胀约 33% 且无法流式处理，
几百张照片时解析会直接吃爆内存。

**关于 `liveStill`（可选，2026-08-06 新增，不升 formatVersion）**：
尺素相机拍的照片会被居中裁成方形（相纸是方的），而**裁过的静态图和没裁的 `.mov` 配不成对** ——
重绘会丢掉 Apple maker note 里的 content identifier。所以这类块会多带一份未裁原图：
`file` 是裁过的方图（显示用），`liveStill` 是未裁原图（**配对用**）。
从相册选的 Live Photo 本来就没裁，只有 `file`，此字段缺席。
**读取方规则：`liveStill` 缺席时就用 `file` 去配对。**

### 2.4 兼容规则（读取方必须遵守）

1. **`formatVersion` 比自己支持的大 → 拒绝导入**，提示「请先更新尺素」。不做半吊子解析。
2. **未知字段一律忽略，不报错**。这样老版本读新包只是丢失新特性，而不是整包读不了。
3. **媒体文件缺失 → 跳过该块，日记其余部分照常导入**，最后汇总告知「N 张照片缺失」。
   宁可残缺也不要整包失败。

## 3. iOS 实施

### 3.1 导出

| 步骤 | 做法 |
|---|---|
| 组装 | 在 `tmp/` 建目录，写 JSON、拷媒体 |
| 打包 | `NSFileCoordinator(.forUploading)` —— **系统自带，能把目录读成标准 zip**，无需依赖 |
| 分享 | `ShareLink` / `UIActivityViewController`，走苹果原生分享面板 |

### 3.2 导入

| 步骤 | 做法 | 落点 |
|---|---|---|
| 接收文件 | Info.plist 注册 `CFBundleDocumentTypes` + `UTExportedTypeDeclarations`，UTI = `com.sinaratech.memoir.backup`。微信/文件 App 里点开会出现「用尺素打开」 | `Memoir/Info.plist` |
| 唤起 | SwiftUI `.onOpenURL`；另有设置 → 数据 → 导入备份走 `.fileImporter` | `ContentView` / `SettingsView` |
| 解压 | ZIPFoundation（§5 决策 1）。**在后台线程跑**，解密 + 解压大包要好几秒 | `BackupImporter.open` |
| 合并 | 按 `id` 去重：已存在的跳过，不覆盖用户现有数据 | `BackupImporter.merge` |
| 结果 | 「新增 42 篇，跳过 6 篇（已存在），1 张照片缺失」 | `BackupImportView` |

**UTI 只声明 `conformsTo: public.data`，不挂 `public.zip-archive`**（与本文档早期草案不同，2026-08-06 改）。
两个原因：① 加密过的包前面有 32 字节自定义头，**根本不是 zip**，声明成压缩包是在撒谎；
② 一旦声明为压缩包，「文件」App 点一下会去**解压**它而不是交给尺素。
扩展名映射本身就够系统识别，不需要那条 conformance。

**标签与心情按「名字」去重，不按 id。** `entries.json` 里的 `tags` / `mood` 存的是名字字符串，
名字才是它们的真实身份；而每台设备首启会各自生成一套默认标签和心情（id 各不相同），
按 id 去重的话，用户导入一次就会多出一整套同名的「生活」「平静」。鸿蒙端请对齐这一条。

**日记本名字按「判重键」比较**（2026-10 起）：去首尾空白 + 忽略大小写 + 忽略全角半角。
包里的日记本与本机同名、且两边都挂着日记时，导入前要问用户「合并 / 作为新日记本导入」，
后者给名字加序号（「旅行 2」），同时改写它名下导入的日记的 `tags`。细则见 `Harmony/CHANGELOG.md` 2026-10-07。
**并进本机同名那本时，本机缺什么补什么、已有的不动**：本机没有照片封面才用包里的 `coverFile` + `coverLayout`（一套），
没有副标题才用包里的 `subtitle`；颜色、书架位置、名字写法都按本机（2026-10-08 P5）。

**`taxonomy.json` 的 `tags` 数组按书架顺序排列**（2026-10 起书架可拖拽排序）。
导入时按数组顺序接在本机书架的末尾。顺序靠数组位置表达，**不加 `sortOrder` 字段**。

**`entries.json` 的 `tags` 最多一个元素**（2026-10 起一篇日记最多属于一本日记本）。
读到多于一个的（旧包），按名字去重后仍多于一个就清空，即只在「全部日记」里。

**`taxonomy.json` 里日记本的照片封面 `coverFile`**（2026-10 起，可选）：指向 `media/` 内的文件名，
是**已经裁好**的封面（宽高比 0.73，宽 1200px 的 JPEG），读取方直接铺满封面即可，不要再裁。
「仅文字」导出不写；字段缺失或文件不在包里 = 没有照片封面（用 `colorID` 的纯色封面），不阻断导入。
不升 `formatVersion` —— 新增可选字段，旧的读取方忽略即可。

**`taxonomy.json` 里日记本的 `coverLayout` / `subtitle`**（2026-10 P3b 起，都可选）：
- `coverLayout`：照片封面的版式，`"FullBleed"`（满版）/ `"Framed"`（白框）/ `"TipIn"`（贴照片）。
  缺失或不认识的值按满版；没有 `coverFile` 时没有意义（「仅文字」导出也不写）
- `subtitle`：日记本主页书名下那行小字，最多 24 个字符，缺失 = 没有

**`taxonomy.json` 里日记本的 `textureID`**：2026-10 起只有 `"Linen"`（皮革下架）。
读取方应**忽略这个值、一律按亚麻处理**，老包里的 `"Leather"` 也一样；
`colorID` 为已下架色时按映射表换成保留色（`Camel` → `AmberBrown` 等）。
字段保留、不升 `formatVersion` —— 取值收窄不影响旧的读取方。

### 3.3 体积与微信限制 ⚠️

微信单文件传输上限约 **100 MB**。一个写了一年、每篇配图的用户很容易超。对策：

- 导出前**预估并显示体积**
- 提供 **「仅文字」** 选项（无媒体，通常只有几百 KB —— 极端情况下的保命通道）
- 提供**时间范围**导出（如「仅 2026 年」）
- 超过 80 MB 时提示改用隔空投送 / 存到「文件」

## 4. 鸿蒙端

## 5. 决策（2026-08-05 已确认）

Amethyst 定的三条优先级，本功能所有取舍都按这个顺序判：
**① 稳定性 ② 小白也能轻松上手 ③ 用户数据隐私（最重要）**

| # | 决策 | 结论 |
|---|---|---|
| 1 | 解压依赖 | ✅ **引入 ZIPFoundation**。稳定性优先，不自己写 zip 解析 |
| 2 | 加密 | ✅ **v1 就要加密**（不推迟到 1.1）。见下方 §5.1 |
| 3 | 导入策略 | ✅ 只做「合并，跳过已存在」，不提供「替换全部」 |
| 4 | 范围 | ✅ v1 只做手动导出 / 导入，定期备份归 CloudKit |
| 5 | 免责声明 | ✅ **导出前必须勾选确认**，不勾不让导出。见 §5.2 |

### 5.1 加密设计

用户设密码 → 用它加密整包。要点：

- **算法**：AES-256-GCM（CryptoKit 自带，无需依赖）。不用 zip 自带的加密 —— 那套弱且各平台实现不一致。
- **做法**：先打包成 zip，再整体加密成一个文件；解密后才是 zip。鸿蒙端按同样方式实现即可。
- **密钥派生**：PBKDF2 或 HKDF，盐随机并写进文件头（明文，不敏感）。
- **⚠️ 忘密码 = 数据永久锁死**，没有后门也不该有。所以：
  - 设密码那一步必须**二次确认**并明确告知「忘记无法找回」
  - 提供**「不加密」选项**，但默认加密，且不加密时警告更重
- 文件头需明文标记 `encrypted: true/false`，让导入端能立刻判断并要密码，而不是解析失败才发现。

### 5.2 免责声明（导出前必须勾选）

未勾选时导出按钮不可用。文案要点（最终措辞待定）：

> 这个文件包含你全部日记的原文、照片与录音。
> - 我们不会看到它，也不会上传到任何服务器
> - 一旦发送给他人或存到第三方（如微信、网盘），它的安全就取决于那个平台
> - 如果设了密码，请务必记住 —— 忘记后我们无法帮你找回

—— 原「需要拍板的四件事」内容保留在下方，作为决策依据留档 ——

## 5.3 决策依据（原始分析）

### 决策 1：解压方案 —— 要不要引入第一个第三方依赖

项目目前是**零第三方依赖**的干净状态。但 iOS 没有公开的解压 API：

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 引入 ZIPFoundation**（MIT，成熟） | 省 2-3 天；zip64、编码等边界都处理好了 | 打破零依赖；多一个供应链面 |
| B. 自己写 zip 读取 | 保持零依赖 | 约 200-250 行；解压本身可用系统 `libcompression` 的 raw deflate，但中央目录解析、损坏包容错要自己扛。**这是在处理用户唯一的一份数据备份，写错了就是丢数据** |

→ **建议 A**。备份恢复是"只能成功不能失败"的路径，不是省一个依赖该冒的险。

### 决策 2：要不要加密

备份包里是用户**全部日记的明文**。发到微信 = 存在腾讯服务器上。

| 方案 | 说明 |
|---|---|
| **A. v1 明文 + 导出前明确警告** | 「此文件包含你全部日记原文，请只发给自己或存到信任的位置」 |
| B. 可选密码加密（AES） | 更安全，但要自己实现加解密（zip 标准加密弱且实现杂），且用户忘密码 = 数据永久锁死 |

→ **建议 A 起步，B 作为 1.1**。但**警告文案不可省**，这是尺素的信任底线。

### 决策 3：导入策略

→ **建议只做「合并，跳过已存在」**，不提供「替换全部」。后者一次误操作就能清空用户所有日记，
收益（少数用户想重置）远小于风险。真要重置，让他们删除重装。

### 决策 4：范围

→ **建议 v1 只做导出 + 导入，不做自动定期备份**。定期备份是 CloudKit 的职责，
在这里重复会让两套机制的边界变模糊。
