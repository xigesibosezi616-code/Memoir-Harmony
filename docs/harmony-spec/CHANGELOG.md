## 2026-10-11

### 🔴 邮筒重做：寄前能挑、投信像真的、寄出不用等（产品决策 + 数据契约 + 行为规则）

**为什么**：用户说「寄出的效果还是太简陋」—— 点一下果冻回弹、然后干等 AI 十几秒，失败了还要再点。
重做成三件事（产品定，2026-10-11）。现状已写进 `03_USER_FLOWS.md` 流程 4，这里是增量。

**① 寄之前看得见、能挑**
- 邮筒页下面一叠「这次寄出的日记」：日期 + 标题（没标题用正文第一行，都没有写「无题」），**默认全勾，可以取消**
- 🔴 **数据契约：`POST /letter` 的 `entries` 只放勾上的那几篇**
- 取消的那篇这次寄完就不再出现（候选规则不变：创建时刻晚于上次寄信）。一篇都没勾时点邮筒不寄

**② 寄的那一下像真的投信**（撤掉果冻回弹 —— 违反「贴着实物、不回弹」）
- 一口气约 3 秒：那叠日记收拢成一页信纸 → 滑进信封 → 封舌合上 → 封口 → 信封举到投信口、上沿往里一倒推进去
  → 投信口翻板被顶开、信进去后落回（闷响）→ 邮戳淡出。时间轴见 `LetterPostingFlight.swift` 顶部的 `LetterPostingTimeline`
- **会员寄出的信封盖自己的火漆**：印面 = 用户昵称首字（没昵称、或首字不是字母 / 汉字时压「素」），和笔友回信盖笔友的火漆对上；
  免费用户是普通封口（同一拍是手指抹平封口）。投信动作人人都有
- 震动 + 声音跟着动画（`LetterPostingFeel.swift` 顶部的表）。声音 `Resources/Sounds/letter_post_sealed.wav` / `letter_post_plain.wav`
  由 `Scripts/make_post_sound.py` 生成，鸿蒙可直接用。减弱动态效果：没有动画，只一下闷响的震动

**③ 寄出不用等**
- 🔴 **投进去就算寄出**：点下的那一刻本地创建 Letter，`status = generating`、正文空、`relatedEntries` = 勾上的日记，
  寄出时刻 / 到达时刻 / 信纸 / 笔友名 / 昵称都在这一刻定下。界面上它就是「在路上」
- 后台寄：成功 → 正文填上、`status = pending`、预约到达通知。断网 / 超时不算失败，过一会儿接着寄（App 被杀，下次回到前台接着寄）；
  服务端出错 1 分钟、5 分钟后重试，**连续 3 次**不成就退回；内容审核没过 / 没登录 / 节奏拦截（先补领，补不到）直接退回
- 退回 = `status = failed`、`errorMessage` = 原因，邮筒页一张退信卡片「重新寄出 / 不寄了」
  - 重新寄出：回到 generating、重试次数清零
  - 不寄了：清空 `relatedEntries`、本机不再管它；记录本身留着（正文空 + failed，哪都不显示），那几篇日记回到候选
- 🔴 **只有投信的那台设备负责寄**：本机另记「哪些信归我寄」（iOS 存 UserDefaults `letterOutbox.v1`，不进同步数据）。
  写信中的信会经云同步到别的设备，那边看到的只是一封写信中的信，不能再寄一次
- 🔴 **重发之前先补领**（`GET /letters`）：服务端有、本机没有、写信时刻 ≥ 这封寄出时刻 − 5 分钟的，就是它的回信（回执丢了），
  直接填进去，**不写第二封**。原先邮筒页的「补领」并进了这里：对不上任何写信中的信的，照旧新落一封
- 「上次寄信时刻」= 写好的信和写信中的信里最晚的寄出时刻；退回的不算；退回那封里的日记不出现在候选里
- 通知权限改到**投信动画放完**再问（原先是第一封写好之后）

**④ 邮戳**：日期（`2026.10.11`）+ 地点。地点取这封信里最近一篇记了地点的日记（`locationInfo` 的第一段，即城市或地标；
中日韩最多 8 个字、拉丁字母 16 个），没有地点就只盖日期。油墨跟主题：素笺 `#B5473A` / 肯特 `#5F7896` / 皮革 `#C8A87C`

**⑤ 提前说明**：进邮筒页就问 `GET /me/rhythm`，`canRequestNow = false` 时状态行按 `reason` 先说清楚，点邮筒只轻轻一顿：

| reason | 文案（中文；七种语言见 xcstrings） |
|---|---|
| `weekly_pending` | 这周的信已经寄出了。{笔友}习惯每周回一次，下周再来寄吧 |
| `daily_cap` | 今天的信已经寄出了，明天再来寄吧 |
| `monthly_cap` | 这个月{笔友}已经回过几封了，下个月再来寄吧 |
| `welcome_pending` | 你的第一封信已经寄出了，{笔友}正在读 |

不写「会在周日前回你」：回信要 6 小时 ~ 3 天才到，周六寄的可能下周二才到。本机还有写信中的信时也先不收下一封
（「上一封信刚寄出，过一会儿再寄下一封」）。问不到（断网）就照常让寄，最终由服务端拦。

**撤销**：果冻回弹、「正在寄出…」干等、失败当场「没能寄出，稍后再试」—— 都没了。

**鸿蒙侧**：
1. 邮筒页加「这次寄出的日记」勾选，`POST /letter` 只发勾上的
2. 寄信改成「先落写信中的信、后台寄、断网续寄、3 次退回」，**本机记哪些信归自己寄**，**重发前先补领**

### 🟡 拆火漆信时的震动和纸声（体验设计，供参考）

**拆信是三下**（产品定）：第一下打碎火漆、第二下打开信封、第三下抽出信纸（抽完自己摊开），每下之间不刻意停顿、也不催；
**急着连点**（这一步还没播完又点了）就不再等，后面几步首尾相接一口气拆完。打碎火漆那一刻算已读。
提示文字跟着步变：「轻点火漆，拆开这封信」→「再点一下，打开信封」→「再点一下，抽出信纸」。

iOS 用 Core Haptics 让震动和纸的声音跟着拆信动画走（时间轴见 `LetterOpeningFeel.swift` 顶部的表）：
火漆裂开是一下清脆重击 + 几下渐轻的碎裂；封舌翻起是一段随速度涨落的低沉持续震动，翻过头顶软软一顿；
信纸抽出是持续的纸张摩擦、中段最强、带纤维颗粒；摊开时轻轻一顿。声音跟着静音键，不打断用户在放的音乐；
减弱动态效果时只轻轻一顿、不放声音。

声音文件 `Resources/Sounds/letter_open_1/2/3.wav`（每步一个）由 `Scripts/make_letter_sound.py` 生成，鸿蒙可直接拿去用。
**鸿蒙侧**：不强制，有余力时用 HarmonyOS 的振动能力（vibrator 自定义效果）按同一条时间轴做一版。

### 🔴 墨迹会干：过去的日记不能被悄悄改写（产品决策 + 数据契约 + 行为规则）

**为什么**：日记的意义在于「当时那样想」。如果过去写下的可以被未来随意改掉、删掉，那就只是一份可编辑的文档。
横向看过：Apple 日记、多数日记 App 随意改不留痕；Day One 随意改但留版本历史；医疗记录是原文不动、增补标日期、删改划线留痕。
尺素取后者的精神，做成纸的规矩（产品定，2026-10-11）。

**规则**

| 规则 | 说明 |
|---|---|
| 什么时候干 | 每一段字**写下 24 小时后**就干了（按这段字自己的写下时刻算，不是按日记）。写日记的当天、补记后的 24 小时内随意改 |
| 干了的字不能删 | 删就是**划掉**：字留着，变淡加删除线，记下划掉的时刻。退格时光标停在划掉的字前面，再退格接着往前划 |
| 取消划掉 | 划掉不到 24 小时的，选中后菜单里可以「取消划掉」 |
| 补记 | 之后再写的字（和日记写下的不是同一天）换一种墨色；整段都是同一天补的，段前标「补记 · 某月某日」（连着几段同一天补的只标第一段） |
| 照片 / 录音 | 干了的可以取下，但原处留一行痕迹「取下了一张照片 · 某月某日」/「删去了一段录音 · 某月某日」，文件删掉 |
| 加粗、荧光笔等格式 | 随时可以加 —— 那是在旧日记上做标记，不是改写 |
| 整篇日记 | **随时可以删**（数据是用户自己的，不拿来当人质） |
| 字数、搜索、寄给笔友 | **不算划掉的字**（划掉就是收回了，只是纸上留着痕迹） |
| 详情页 | 日期下面一行「补记 N 次 · 最近 某月某日」 |

**数据**（时间一律 Unix 秒，`Double`）
- `TextStyleRun` 多两个可选字段：`writtenAt`（这段字什么时候写的，nil = 日记写下时就有）、`struckAt`（什么时候划掉的）
- 照片块、录音块多一个可选的 `addedAt`（什么时候放进来的，nil = 日记写下时就有）
- 内容块多一种 `type: "trace"`，字段 `traceOf`（`"photo"` / `"audio"`）、`removedAt`
- 判断「干没干」的基准是日记的 `createdAt`（真正写下的时刻），不是用户可以改的 `date`
- **备份包**：`styles` 原样带上这两个新字段；`BackupBlock` 加 `addedAt` / `traceOf` / `removedAt`，`type` 可以是 `"trace"`。都是可选字段，不升 `formatVersion`

**鸿蒙侧要做**：按上表实现编辑规则（删除转划掉、补记标注、取下留痕、详情页补记次数），读写这些字段；内容块逐块容错（认不出的 `type` 跳过）。

### 🔴 图文编辑器：整篇连续编辑、文字绕照片排、基础格式（数据契约 + 产品决策）

**为什么**：原来正文是一段段独立的输入框拼起来的，长草稿滑不动、段落之间分不清、照片只能插在两段之间且多张会乱排。

**数据**：`ContentBlock`（文本块）多一个可选字段 `styles`，备份包 `BackupBlock` 同样多一个 `styles`，**不升 `formatVersion`**
（⚠️ 10-10 第一版提交时漏了备份包这一侧，同日已补上，见下面「录音放进正文」那条）：

```json
{ "type": "text", "text": "……", "styles": [ { "location": 13, "length": 4, "bold": true },
                                            { "location": 0, "length": 4, "heading": true } ] }
```

- `location` / `length` 按 **UTF-16** 计，相对这个文本块的 `text`；`bold` / `italic` / `heading` 都可选
- `text` 仍是**纯文字** —— 笔友回信、字数、摘要只读它；不认识 `styles` 的版本照样能显示正文
- 小标题是整段的格式，同样用区间表示

**行为**：
- 正文是一整篇连续编辑；照片浮在所在段落的左边或右边，**文字绕开照片排**（相纸、倾斜保留）
- 照片在光标处插入：光标在段尾 → 挂到下一段开头；段首 → 就挂这段；段中间 → 断成两段，挂后一段开头
- 点照片：靠左 / 靠右、设为封面、换相纸、删除；长按拖到别的段落、左右半边决定靠哪边
- 退格碰到照片先选中，再按一次才删
- **详情页不再能插照片**（原来长按正文的「在此处插入照片」已去掉，产品定）；加照片统一在写日记页、编辑页
- 写日记页、编辑页、详情页同一套排版（素笺 17 号字，皮革 / 肯特 14 号字）

**鸿蒙侧要做**：读写 `styles`（没有就当无格式）；正文编辑按上面的规则；详情页去掉插照片入口。

### 🔴 尺素会员：火漆信（数据字段 + 备份包字段 + 行为规则）

会员寄出的信装在**火漆封口的信封**里，第一次打开要拆；拆开是**专属信纸**（字一行一格落在格线上）。免费用户的信不变。
界面鸿蒙可按自己的规范重做，**下面的数据和规则两端必须一致**。

**数据**：信件多一个可选字段 `stationery`（iOS `Letter.stationery`，schema V8）。

| 取值 | 含义 |
|---|---|
| 空 | 普通信纸（免费，以及所有老信件） |
| `"sealed"` | 火漆信（会员） |

- **寄出那一刻**按当时的会员身份写定，之后不再改。会员到期后，**已经收到的火漆信保持火漆**（`MEMBERSHIP.md`「会员到期之后」）。显示时**不要**实时读会员状态来决定信纸
- 从服务器补领丢失的信（服务器不记信纸）时，按补领时的会员身份算
- **备份包 `letters.json`** 的每封信多一个可选的 `stationery`，**不升 `formatVersion`**：老包、鸿蒙包没有这个字段 → 普通信纸；不认识的取值原样保留。火漆信导回来还是火漆信，不看导入时是不是会员

**行为规则**：

| 规则 | 说明 |
|---|---|
| 火漆上的字 | **笔友名字的首字**（信是笔友封的，现实里是寄信人用自己的印；拉丁字母取大写，取不到用「素」）。注意和付费页那枚不同 —— 付费页压的是用户自己的名字 |
| 什么时候算已读 | 普通信：打开即已读。火漆信：**点开信封拆开的那一刻**才算已读；只看了一眼信封就退出，信还封着 |
| 信箱列表 | 没拆的火漆信不显示正文预览，显示「火漆封着，还没拆」—— 拆开才读到内容 |
| 拆过的火漆信 | 再打开直接摊开信纸，不再走拆信 |
| 减弱动态效果 | 系统开了就不播拆信过程，点一下直接换成信纸 |
| 拆信过程（iOS） | 火漆沿封舌裂开 → 封舌带着上半块火漆翻上去 → 信纸抽出 → 摊开成信纸。约 3 秒，平滑曲线、无回弹。鸿蒙可自行设计，但别做成数码感的弹跳 |

**鸿蒙侧要做**：信件模型加 `stationery`、寄信时按会员身份写入、备份包读写这个字段；信箱和读信按上表实现。

### 🔴 笔友回信的语言：跟着日记写的语言走（七种）

**为什么**：iOS 原来按**系统语言**决定回信语言（还只分中 / 英两档）。系统英文、App 繁中、日记写中文的用户
收到了英文信；繁中被当简中，日韩法西一律英文。

**规则（产品定）**：你用什么语言写，笔友就用什么语言回，繁简也跟着日记。
在**本机**识别这次寄出去的日记（标题 + 正文），不额外上传任何东西；认不出来时用 **App 的语言设置**。

| 识别规则（iOS `LetterLanguage`，鸿蒙照此对齐） | 说明 |
|---|---|
| 少于 12 个字 | 不识别，用 App 语言 |
| 先按文字系统分大类，汉字一个、拉丁字母一个词各算一票 | 直接丢给识别器的话，中英混写会被认成英文（实测） |
| 韩文字母占多数 → `ko` | |
| 汉字 + 假名占多数：有假名（≥2 个且 ≥ 十分之一）→ `ja`；否则**只拿汉字**分简繁 | 夹着的英文会把简繁识别带偏；简繁写法一样分不出来时用 App 语言 |
| 拉丁字母占多数 → 在 en / fr / es 里挑 | |
| 置信度 < 0.6 | 当作认不出，用 App 语言 |

**接口**：`POST /letter` 的 `language` 扩到七种，见 `02_BACKEND_API.md`。老值 `zh` / `en` 照旧。

**鸿蒙侧要做**：别用系统语言或界面语言，按上表识别日记的语言再传（HarmonyOS 有文本语种识别能力，结果对齐到这七个代码即可）。

### 🔴 App 内注销账号（上架硬性要求）

**为什么**：Apple 审核指南 5.1.1(v) 要求支持注册账号的 App 必须能在 App 内注销，「发邮件给我们」不算数；
国内《个人信息保护法》也要求提供注销途径，华为应用市场同样会查。之前两端都没有，隐私政策写的是「邮件申请」。

**接口**：`POST /me/delete`，详见 `02_BACKEND_API.md`。删服务器上的账号、登录绑定、来信、订阅记录、权益。

**流程（iOS 现状，鸿蒙照此对齐行为，界面可按鸿蒙规范重做）**：
设置 → 账户 → 最下面红色「注销账号」（和退出登录分开一组）→
① 说明页：**会删除**（服务器上的账号、绑定的手机号和 Apple ID、昵称、笔友称呼、来信记录）/
**不会删除**（本机和云端里的日记、照片、录音、已收到的信）/ **无法恢复**（同一手机号可以再注册，但是全新账号）→
② **验证是本人**：给当前绑定手机号发验证码；绑了 Apple ID 的也可以重新走一次 Apple 登录 →
③ 二次确认「此操作无法撤销」→ 删除成功后清掉本地登录态、退回设置首页。

| 规则 | 说明 |
|---|---|
| 必须再验身份 | 只有登录态不够。验证码只对**账号绑定的号**校验 |
| 本地数据一律不动 | 日记、照片、录音、已收到的信都留在用户设备和云端 |
| 吊销第三方授权 | iOS 用 Apple 验证时，服务端拿授权码吊销「通过 Apple 登录」授权（Apple 要求）。**鸿蒙若接华为账号登录，同样要撤销华为授权** |
| 删除次序 | 先删来信 / 订阅 / 权益，再删账号，**最后**删登录绑定 —— 中途失败时用户还能重新验证、再点一次 |
| 错误提示 | 写在注销页上，不要用全局提示条（iOS 实测会被弹出页挡住） |

**鸿蒙侧要做**：设置里加注销入口，走验证码方式调 `POST /me/delete`；成功后清本地登录态。隐私政策同步改成「App 内自助注销 + 邮件兜底」。

### 🔴 同名日记本合并：本机缺什么补什么（P5）

V7 给日记本加了照片封面、版式、副标题，但合并规则原先只管「日记挂到哪本」。现在定下这三样怎么合：
**留下的那本缺什么就补什么，已有的一律不动**。封面照片和版式是**一套**（版式只对照片封面有意义），副标题单独看。

| 场景 | 留下的是哪本 | 规则 |
|---|---|---|
| 导入备份，并进本机同名那本（用户选「合并」，或一边是空本子不问直接合） | 本机那本（同一个判重键本机有多本时取最早建的，和改写名字时挑的同一本） | 本机**没有照片封面** → 拿包里的 `coverFile` 文件 + `coverLayout`；本机**没有副标题** → 拿包里的 `subtitle`。颜色、书架位置、名字写法都按本机 |
| 包里自己就有「Travel」「travel」两种写法 | 先出现的那本 | 后一本并进前一本，同上 |
| 回到前台的同名去重（多设备同步造成） | 按 (`createdAt`, `id`) 最早那条 | 它没有照片封面 → 按同一个顺序取**第一个有封面的**，封面 + 版式整套转过来；它没有副标题 → 取第一个非空的副标题 |

> 之前的去重只转封面文件名、不转版式 —— 另一台设备上选的「白框」会变回默认的「满版」，副标题直接丢。
> 去重的取值顺序**必须是确定的**（两台设备各自去重，转的得是同一份），理由同 2026-10-07 那条。

**鸿蒙侧要做**：导入的「合并」分支、前台去重都按上表补字段；「作为新日记本导入」不变（本来就整套带过来）。

### 🔴 封面编辑器（P3b）：三种版式 + 调整构图 + 副标题

「…」→ **编辑封面**（原「更换封面」改名）。编辑页从上到下：预览 → 封面照片 → 版式 → 颜色 → 副标题。

**版式**（只对照片封面生效，存日记本的 `coverLayoutID`，备份字段 `coverLayout`）：

| 版式 | rawValue | 书架上的封面 | 日记本主页大图 |
|---|---|---|---|
| 满版 | `FullBleed` | 照片铺满，书名压在照片上（P2 那种） | 照片铺满，往下融进底色 |
| 白框 | `Framed` | 米白纸封面：抬头是篇数 + 一道细线，照片嵌成方形，书名写在照片下面（参考图 ② 的 CHRONICLE） | 整幅米白纸，照片嵌在中间，书名、副标题在下 |

- 书架上拿起书转过去露出的**书脊颜色跟着版式**：满版 = 照片主色，白框 = 纸色，贴照片 / 纯色 = 布面颜色
- 颜色这一栏只在**没有照片**、或版式是**贴照片**（底子是布面）时出现；贴照片时小标题叫「布面颜色」

- 原来就有的封面：原图没留，只能在已裁好的那张里再调（只能更紧，不能更松）
- 放大后取景框里的像素不到 1200 宽时，**按实际像素存，不硬拉伸**

**副标题**：可选，最多 24 字，去首尾空白，空 = 没有。显示在日记本主页书名下；不写时主页显示这本日记跨越的年月。

### 🔴 日记本照片封面（P2）

### 🔴 书架改版：一层层的书架板 + 长按拿起一本、换个位置放回去

**要的感觉**（产品负责人原话）：像从真的书架上拿一本书、换个地方放回去，**丝滑且温柔**。
真正的书架和日记本不会抖 —— 所以**不要做成桌面图标那种整理模式**（iOS 第一版这么做过，已被否掉）。

**交互规则（两端一致）**：

| 步骤 | 被拿起的那本 | 其余的书 |
|---|---|---|
| 长按一本（约 0.35 秒） | 绕自己的竖轴**同轴转过去**一个角度（iOS 用 32°），露出书脊，轻轻浮起 | **一动不动** |
| 拖着走 | 跟着手指走，保持转过去的姿态；原来的位置**空着**（像真的从架子上抽走了一本） | **一动不动**：不晃、不让位、不出角标 |
| 拖到屏幕上下边缘 | 书架自动滚动 | — |
| 松手 | 先**落进手下最近的那个位置** | 这时才**轻轻挪开**让出位子 |
| 落定之后 | 再**同轴转回正面** | — |

- 全程用**不过冲的平滑曲线**，不弹、不晃
- 落点 = 离书中心**最近的那一格**（按插入算：放在某本的位置上，那本和后面的顺延）。松在格子缝里、拖过了最后一本，也都有确定的去处
- 「全部日记」固定第一格，不能拿起
- **换封面 / 重命名 / 删除**：原来书架上的长按菜单**取消**（长按现在用来拿书），挪到**日记本页右上角的「…」**。
  「全部日记」页没有这个菜单
- 书架顺序 = 日记本的 `sortOrder`（小的在前；相同时按创建时间）。**新建的日记本一律排最后**（现有最大值 + 1），
  包括写日记时顺手建的、导入的、首启默认的四本（0~3）
- 老数据迁移上来 `sortOrder` 全是 0，按创建时间排 = 原来的顺序，不需要回填
- 备份包：`taxonomy.json` 的日记本按书架顺序排列，导入时按这个顺序接在书架末尾（见 `EXPORT_FORMAT.md`）

> 💡 iOS 的书脊是真的 3D：封面和书脊当成一个长方体的两个面，各自算投影、共用同一根转轴和同一个透视，
> 交界才对得上（平台自带的单面 3D 旋转只能转一张卡片，看不到厚度）。鸿蒙按平台能力做，转过去时**能看到书的厚度**是关键。

### 🔴 日记本：名字不许重复，判重规则两端必须一致

日记靠**名字字符串**挂在日记本上（`entries.json` 的 `tags`），两本同名的日记本在数据上根本分不开。
所以名字就是身份，判重规则两端不一致的话，同一个包在两端导入的结果会不一样。

**判重键 = 去首尾空白 + 忽略大小写 + 忽略全角半角**。「Travel」「travel」「Ｔｒａｖｅｌ」「 旅行 」各算同一个。
存库时只去首尾空白，大小写和全半角**原样保留**用户输入的样子。

所有能产生日记本名字的入口都要拦：新建、重命名、写日记页里顺手新建、导入。
- 新建 / 重命名撞名：**当场说明**「已有同名的日记本」（iOS 以前重命名撞名是静默不保存，用户只看到改了没反应）
- 写日记页顺手新建时撞名：**直接选中已有那本**，不报错（用库里那本的原名）

**同名记录的事后合并**：新设备首启时云同步往往还没到，会先建一套默认日记本，同步下来又是一套。
iOS 每次回到前台把**完全同名**的记录合成一本，规则：
- 按 (`createdAt`, `id`) **取最早的那条**，删其余。**必须是确定性的** ——
  两台设备会各自合并再把删除同步给对方，若 A 留 X、B 留 Y，同步完两条都没了
- 只合**完全同名**的。仅大小写 / 全半角不同的（新规则之前用户自己建的）挂着不同的日记，**不动**

### 🔴 导入备份：同名日记本要先问用户（合并 / 作为新日记本导入）

**什么时候问**：包里的日记本与本机的**按判重键同名**，而且**两边都挂着日记**。
「包里那边」只算这次真会新增的日记（id 本机没有的）。

> 不这么筛的话，两台设备都有默认的「生活 / 旅行…」，几乎每次导入都会弹窗；
> 重导同一个包时那些日记全会跳过，也不该问。一边是空本子时直接合并，不打扰用户。

**两个选项**（加一个取消）：

| 选项 | 效果 |
|---|---|
| 合并到同名日记本 | 导入的日记放进本机已有的那本。包里写法不同的（「travel」）改写成本机的写法（「Travel」） |
| 作为新日记本导入 | 另建一本，名字加序号：「旅行」→「旅行 2」，被占用就继续往后 →「旅行 3」。它名下导入的日记跟着改名 |

起序号时要避开的名字：本机的日记本、本机日记上挂着的名字（含已删日记本留下的）、**包里自己的全部名字**
（包里可能本来就有一本「旅行 2」）。序号格式是「名字 + 半角空格 + 数字」，**不随语言变**（它是用户数据）。

只有被问到的那几本才受选项影响，其余同名的一律合并。
包里自己就有「Travel」和「travel」两种写法时，导入后并成一本。

> 💡 iOS 实现在 `BackupImporter.planTagNames`：先算出「包里每个名字 → 导入后叫什么」的表，
> 日记本定义和日记上挂的名字都按这张表改写。问不问、怎么改都从这一张表出，不会两处对不上。

### 🔴 日记本封面：皮革下架，只留亚麻，不再让用户选材质

**产品决策**：纯色布面只是「还没换照片时」的底子，封面的主角要留给用户自己的照片

### 🟡 后端返回的日期**一定带毫秒**，客户端解析必须认小数秒

后端所有日期都是 `new Date(...).toISOString()`，形如 `2026-09-17T10:20:30.123Z`。

iOS 侧踩到的坑：`JSONDecoder` 内置的 `.iso8601` 策略**不认小数秒**，
一旦有哪个响应字段被声明成日期类型，**整条解码都会失败**，而且报的是
「数据损坏」这种看不出所以然的错。已改成两种格式都认（带/不带小数秒）。

**鸿蒙侧**：解析后端日期时同样要兼容带小数秒的格式，别直接用只认秒级的解析器。

### 🔴 求信必须能「补领」——否则信丢了、额度还被扣

**真机暴露的问题**：两台设备，一台每次求信都被拦（提示「请求过于频繁」），一台寄出成功
但三天没等到回信。查下来是同一条链路上的三个缺陷。

**服务端的时序是「AI 写完 → 先写库 → 再把正文放响应里返回」，而来信节奏的额度是按库里的
行数算的。** 所以只要响应没回到客户端（模型慢导致超时、断网、App 被切走），
那封信就是：**在服务端存在、在用户手上不存在，而这一周的额度已经没了** ——
之后每次求信都是 429，用户永远等不到那封信。

**鸿蒙侧要做的**：

- 🔴 **必须实现补领**：进邮筒页时、以及被 429 拦下时，调 `GET /letters` 把服务端有、
  本机没有的信拉回来落地。**只有 `POST /letter` 那一次响应是唯一送达路径的话，
  这个 bug 一定会复现。**
- **按正文去重**（iOS 侧的做法）。如果鸿蒙端有删除来信的功能，去重就不能只看正文，
  否则会把用户删掉的信复活 —— 那种情况需要额外记服务端 id。
- **补领回来的信，到达时刻按服务端的 `generatedAt` 重算**（`generatedAt + 6 小时~3 天`，
  见 2026-09-14 的投递规则）：早就过了三天的即刻到达，刚写好的仍然在路上。

### 🔴 节奏拦截的文案由客户端按 `reason` 渲染，不要直接显示后端那句

后端 429 的响应体里有 `reason`（`weekly_pending` / `daily_cap` / `monthly_cap` /
`welcome_pending`）和一句中文 message。**那句 message 只有中文** ——
直接透传会让日/英/韩/法/西用户看到一句突兀的中文。

iOS 侧改成按 `reason` 自己渲染七种语言（中文与后端 `rhythmMessage` 一字对应，
其余六种按各自语境重写）。鸿蒙端同理。

⚠️ 之前 iOS 的 bug 是**连 reason 都没看**，直接把 429 显示成「请求过于频繁，请稍后再试」——
这既是 SaaS 计量词（定价文档 §5.1 明令禁止），又让用户完全不知道真实原因
（陈总看到的就是这句，实际原因是「本周的信已经到了」）。

### 🟡 模型调用必须设超时，而且要比客户端先放弃

`ai-deepseek` / `ai-openrouter` 原先的 `fetch` **没有任何超时**，模型一卡服务端就一直挂着。
客户端 90 秒放弃后，服务端可能过一会儿才写库成功 —— 这正是上面「信丢了额度还被扣」的源头。

现在两个 adapter 都是 **75 秒**（< 客户端的 90 秒），超时就干脆失败、不写库，用户重试即可。
鸿蒙端如果自己直连模型，同样要保证「服务端比客户端先放弃」。

## 2026-09-10

### 🔴 账号：绑手机号可能**换账号**，`POST /me/bindings/phone` 的响应变了

**这是本次最要紧的一条 —— 契约变了，不跟进会让用户卡在进不去自己账号的死局里。**

场景：用户以前用手机号注册过（userA，有来信有订阅）。换新设备后他先点了
**第三方登录**（Apple / 华为），服务端查不到这个第三方身份，于是**建了个新空账号 userB**。
接着引导他绑手机号，他填的正是自己原来那个号 —— 而那个号已经属于 userA。

**旧行为是直接 409**。但用户没做错任何事，却再也进不去自己的账号。

**新行为**：当 userB 是**空壳**（服务端没有属于它的来信 / 订阅 / 权益，也没设过昵称）时，
服务端把 userB 的第三方绑定**转移**给 userA、删掉 userB，让用户直接进入原账号。

> ⚠️ 这**不是账号合并**（`AUTH_DESIGN.md §1.5` 明确不做合并）。
> userB 是个刚出生、什么都没有的空壳，所以可以安全清理。
> 只要 userB 有任何数据，就仍然 409。
>
> 注意判据里**不包含本地日记** —— 日记存在设备和用户自己的云盘里，与账号 id 无关，
> 换账号不会丢。鸿蒙侧判断"这个账号是不是空的"也不要把本地日记算进去。

响应结构（`BindPhoneResponse`）：

```jsonc
// → 200
{
  "ok": true,
  "switchedAccount": true,     // 🔴 发生了账号转移
  "token": "<新账号的 JWT>",    // switchedAccount 为 true 时才有
  "user": { /* UserDTO，注意这是**原账号**的档案，昵称也是原账号的 */ }
}
```

**鸿蒙侧要做的**：

- `switchedAccount == true` 时，**必须用返回的 `token` 覆盖本地那个**。
  本地旧 token 指向的 userB **已经被删了**，继续用会 401。
- 同时用返回的 `user` 覆盖本地用户快照 —— 昵称、绑定列表都换成原账号的。
- UI 上给一句提示，让用户知道自己回到了原来的账号（不然他会以为昵称莫名其妙变了）。
- `switchedAccount == false` 就是原来的普通绑定成功，照旧处理。

### 🔴 新接口 `POST /me/bindings/phone/change`（换绑手机号）

之前没有换绑能力，用户换号就等于丢账号。

```jsonc
// 请求：旧号证明「是本人」，新号证明「号是你的」，缺一不可
{ "oldCode": "123456", "newTarget": "13900139000", "newCode": "654321" }
// → 200 { "user": { /* UserDTO */ } }
```

两个验证码都走现成的 `POST /auth/send-code` 发，`oldCode` 发给**当前已绑的号**，
`newCode` 发给**新号**。

**行为规则（两端必须一致）**：

- 新号已属于**别人** → **409**，一个字都不写库（否则能把别人的账号抢过来）
- 新号就是**自己当前这个号** → 幂等放过，不写库，不报错
- 当前账号**压根没绑过**手机号 → 400（该走绑定而不是换绑）

### 🟡 验证码防刷：时间比较全部挪进 SQL（线上 bug 修复）

三层防刷（同号 60 秒冷却 / 同号 24 小时 8 次 / 同 IP 每小时上限）原先把 `created_at`
取到 JS 里跟 `Date.now()` 比。`created_at` 是数据库用 `CURRENT_TIMESTAMP` 生成的
`DATETIME`，**不带时区**；驱动却按**进程时区**解析它 —— 函数计算容器是 UTC、RDS 是 +08:00，
读出来凭空多 8 小时。后果：冷却算出「请 28860 秒后重试」，24 小时窗口被撑成 32 小时，
用户直接收不到验证码。

现已全部改成在 SQL 内比较（`TIMESTAMPDIFF` / `NOW() - INTERVAL ...`），两边同在数据库时区里。

**鸿蒙侧要做的**：接口行为不变，**不用改代码**。但如果鸿蒙端自己也有碰
「数据库生成的时间」的地方，照这个写法办 —— 别把时间取到应用层再比。

> ⚠️ 这段 SQL 用的是 **MySQL 方言**，海外版（Postgres）跑到这儿会直接报错，启动前要处理。

### 🔴 抬头的译文：不要在代码里拼「致」+ 昵称

这条是**行为规则**，两端必须一致，鸿蒙端做多语言时会踩到同一个坑。

抬头**整句**交给译文排，占位符只放昵称 —— 因为**各语言的语序不同**：

| 语言 | 抬头 |
|---|---|
| 简中 / 繁中 | `致%@` |
| English | `Dear %@` |
| 日本語 | `%@へ` ← **名字在前** |
| 한국어 | `%@에게` ← **名字在前** |
| Français | `À %@` |
| Español | `Para %@` |

在代码里写成「致」+ 昵称的拼接，日文就会变成「致海绵宝宝」——语序是错的。

**法语 / 西班牙语刻意用了中性译法**（`À` / `Para`，即「致」），
没用 `Cher`/`Chère`、`Querido`/`Querida` —— 那几个词分阴阳性，
而我们**不知道用户昵称的性别**，猜错就是当面叫错性别。

**没有昵称时**（没登录 / 没设昵称）退回单独的「致」那条 key，不要显示空的抬头。

   那些**在调用时读一次配置**的地方（格式化日期、从代码里主动取译文的工具函数）
   不重新调用就还是旧语言，表现是**切了一半** —— 一半界面新语言、一半旧语言。
   iOS 的解法是切换时**强制重建整棵视图树**。鸿蒙端如果也有类似的"取一次就缓存"的
   本地化调用，务必一起验。
3. 🔴 **组件的文本参数类型决定了会不会被翻译**。iOS 上一个设置项行组件的标题参数写成了
   普通字符串，后果是**整个设置页在任何外语下都显示中文**，而且**工具链根本不会
   把这些文案收进翻译表** —— 连"漏翻了"这件事都看不见，藏了大半年。
   鸿蒙端请检查自己的通用行/卡片组件：**文案参数要用能被提取的本地化类型，
   用户数据（昵称、地名、店名）才用普通字符串**，两者在调用处要能一眼分辨。

> 💡 iOS 侧为此加了一条自查命令（`Scripts/check_localization.py`），
> 能报出「代码里有这句中文但翻译表里没有」「六种语言没齐」「从字符串函数里直接返回中文」
> 三类问题，干净时退出码 0，可以挂 CI。**建议鸿蒙端也搞一个同类脚本** ——
> 靠人肉记住六种语言是不现实的。

### 🔴 写日记页加了草稿：重新定义了「什么算完成了一篇日记」

这是**产品语义的改动**，两端必须一致，否则同一个用户在两台设备上对"我的日记有几篇"的
认知会对不上。

**新规则**：

| 动作 | 结果 |
|---|---|
| 点右上角**对勾** | **这才叫「完成了一篇书写」** —— 这一刻才产生一篇正式日记 |
| 点左上角**返回** | 弹确认框：**不保存** / **保存草稿**。存草稿**不产生日记** |
| 点**不保存** | 这篇就此作废，连同已存在的草稿一起丢弃 |
| 正文完全为空时点返回 | 不弹框，直接退出（别拿弹窗打扰什么都没写的人） |

**草稿全局只留一份**，下次进写日记页自动接着写，顶部给一行「接着上次没写完的」告诉用户
这不是空白页。没有草稿箱、没有多份草稿列表 —— 日记场景同时开好几篇的情况极少，
尺素的性格是克制。

**iOS 侧的实现选择（鸿蒙可自行决定，但坑是共通的）**：草稿单独建了一张表，
**没有**在日记表上加 `isDraft` 标志位。理由：加标志位的话，首页、日记本、搜索、
大屏展示、备份包导出、字数统计……**每一处查询都得记得加过滤条件，漏一处草稿就混进正式日记里**。
独立的表从类型上就杜绝了这件事。

**🔴 鸿蒙侧必须注意的三件事**（这三条 iOS 都踩过或专门防过）：

1. **草稿引用的照片会被"清理孤儿文件"误删**。
   照片在插入那一刻就落盘了，但此时还没有任何**日记**引用它 ——
   孤儿回收如果只按日记的引用来算，用户存了草稿再清一次缓存，草稿里的图就没了。
   **草稿的引用必须算进"在用"**。
2. **草稿转正时只删草稿记录，绝不删它引用的媒体文件** —— 那些文件正要被新日记接着用，
   删了就是有字没图。
3. **「不保存」= 整份草稿作废**（连同它引用的媒体文件一起删）。
   曾经按"只丢弃本次修改、保留原草稿"实现过，用户实测反驳：
   弹窗上写着「保存这篇草稿？」，按下「不保存」表达的是**这篇我不要了**。
   误触的出口应该是**点遮罩取消**（回到编辑），而不是让「不保存」变得半吊子。

**草稿里的「此时此地」原样保存、恢复时不重新定位**：草稿可能是昨天在广州写的，
今天在西安打开，重新定位会把地点改成西安，可这篇日记记的是昨天那件事。
用户手动挑过的地点更不能被覆盖。

### ⚪️ 写日记页改为全屏呈现

iOS 原来是半屏卡片（sheet），改成全屏，并去掉了下滑关闭手势 ——
退出统一走返回键的确认框，避免"手一滑内容就没了"。
左上角图标也从**叉叉**换成**返回箭头**：退出不再等于丢弃，叉叉的语义已经不对了。

鸿蒙端按 HarmonyOS Design 自行决定呈现方式，**但请保证"退出前有一次挽回的机会"这条行为一致**。

### 🟡 媒体文件的同步：一个两端都躲不掉的坑

iOS 端踩了这个，鸿蒙端做自己的同步时**一定会遇到同一个问题**，先说在前面。

**问题**：照片 / 录音 / Live 视频是**磁盘上的独立文件**，数据库里只存文件名。
所以只同步数据库的话，同步到第二台设备的日记**有字没图** —— 而且不会报任何错，
用户看到的就是一篇篇残缺的日记。

**iOS 的解法**（思路可借鉴，具体 API 不通用）：
新增一个 `MediaAsset` 表，用「外部存储的二进制字段」装文件字节，
让同步框架把它当附件自动带走；读取路径完全不改，靠两个**对账**函数补齐两个方向：

| 方向 | 做什么 |
|---|---|
| 本地 → 云 | 被日记引用、但还没登记的文件，补一条记录 |
| 云 → 本地 | 已同步下来、但本机磁盘上没有的，写回磁盘 |

**为什么是「事后对账」而不是「写入时双写」**：照片的写入点散在写日记页、详情页插图、
备份包导入等好几处，逐个改双写既啰嗦又迟早漏一个。
以「库里引用了什么」为唯一依据来补，天然覆盖所有写入路径，包括以后新加的。
**鸿蒙端建议照这个思路做**，别在每个写入点手工双写。

配套：删日记 / 清理孤儿时**必须连云端记录一起删** ——
只删本地的话，下次同步会把它又拉回来，清理就白做了。

### ⚪️ iOS 的 schema 迁移踩坑（鸿蒙用的是别的持久化方案，仅供参考思路）

iOS 的版本化 schema 里，旧版本的定义引用的是**当前活着的类型**而不是当时的快照。
后来给某个 model 加了一条指向新 model 的关系，这条关系把新 model **拽进了旧版本的模型图**，
导致新旧两个版本在框架看来完全相同，迁移计划直接崩。

**可迁移的教训**：
1. 版本快照就要是**快照**，不能引用会继续演化的活定义
2. **「容器能初始化」不等于「迁移能跑」** —— store 已经在最新版时根本不走迁移路径。
   验收必须**用旧版本的库真跑一次升级**，否则问题要等真实用户升级才爆

## 2026-08-06

### 🔴 备份包格式定稿 v1（`formatVersion = 1`）—— 这是两端之间**唯一**的数据通路

iOS 端导出 + 导入**全链路已完成并验收**。契约在
[`Memoir/Docs/EXPORT_FORMAT.md`](../EXPORT_FORMAT.md)，鸿蒙端按它实现**读取**即可开始。

**鸿蒙侧要做**：实现 `.memoir` 包的读取。要点：

- 容器是标准 ZIP（`@ohos.zlib` 可解）；**加密包不是 zip** —— 前面有 32 字节自定义头，
  魔数 `MEMOIRBK`，需先 PBKDF2-HMAC-SHA256（21 万轮）+ AES-256-GCM 解密才得到 zip
- **iOS 导出的包会多套一层同名目录**（`尺素备份_20260805/manifest.json`），
  解压后要**往下找一层**才是包根，不能假定 manifest 在顶层
- **标签与心情按「名字」去重，不按 id**。日记里存的是名字字符串，名字才是身份；
  按 id 去重的话用户导一次就多出一整套同名的「生活」「平静」
- **合并策略只有一种：按 id 跳过已存在的，绝不覆盖**。导入在任何情况下只让库里变多，不变少
- **缺字段不要整包拒收**，只有 `formatVersion` 必须可信（比自己支持的大就拒绝，提示更新 App）
- 媒体缺失只丢那一块，日记其余部分照常导入，最后汇总告知

### 🔴 `liveStill` 字段（备份包 `blocks[]` 内，可选，**不升 formatVersion**）

尺素相机拍的照片会被居中裁成方形（相纸是方的），而**裁过的静态图和没裁的视频配不成对**。
所以这类块多带一份未裁原图：`file` = 裁过的方图（显示用），`liveStill` = 未裁原图（**配对用**）。

**鸿蒙侧要做**：读取时按「`liveStill` 缺席就用 `file` 去配对」处理。

### 🔴 Live Photo 的铁律：静态图**绝不能重新编码**

iOS 这边踩了个大坑，鸿蒙端做 Live Photo 时会遇到同一类问题，写下来避免重蹈覆辙：

Live Photo 的静态图里藏着一个 **content identifier**（iOS 在 Apple maker note 里），
系统靠它把静态图和视频配成一对。**只要把图读进内存再编码一次（哪怕不改画质），这段元数据就没了**，
配对永远失败。而且失败是**静默的** —— 不报错，只是返回空。

iOS 端因此出过两个用户可见的 bug：长按不播、以及**照片整个不显示**（配对失败时播放器渲染成空白）。

**鸿蒙侧要做**：
1. Live Photo 的静态图**原样落盘**，别走"解码再编码"的路径
2. 播放器组件**必须有静态图兜底** —— 配对失败时显示静态图，**绝不能什么都不显示**
3. 配对失败要**打日志**，否则永远查不到

### 🟡 撤销：3D 视差效果（两端都不做）

iOS 端整体删除。原因写在 [`04_DESIGN_LANGUAGE.md`](04_DESIGN_LANGUAGE.md) 的「视差」一节 ——
整张照片平移做不出纵深、模拟器无法验证、静默失效的坑多。

**鸿蒙侧要做**：**不要实现**。`01_TECH_STACK_MAPPING.md` 里陀螺仪那一行已标注撤销。

### 🟡 照片手势改版：点击和长按**都是打开全屏**

正文里的相纸太小，Live Photo 在那么一格里播没什么意思，放大了看才对得起它。
照片的编辑操作（换边 / 换相纸 / 删除）也从「正文里长按」统一挪到**全屏页右上角的「⋯」**，
所有照片一个入口，用户不用记「哪种照片长按会出什么」。

**鸿蒙侧要做**：交互对齐（UI 可按 HarmonyOS Design 重画，行为一致即可）。

### 🟡 刻意**不给** Live Photo 加 LIVE 角标

相纸是「实体照片」的隐喻，贴一个系统风格的标签就破功了；
而且预告了的惊喜就不是惊喜 —— live 静静存着，用户哪天长按了自己发现。

### 🟡 相机拍照**一律存一份进系统相册**，不给开关

日记正文里放的是裁过的方图，完整那张不落到相册就等于拍完即弃。
用户在尺素里按快门，拍到的东西理应和用系统相机一样留在相册里。

**鸿蒙侧要做**：对齐这个行为（鸿蒙的媒体库 API 自行选型）。

### 🟡 账号加了「昵称」入口（`displayName`）

后端 `PATCH /me` 早就支持 `displayName`（限长 64，空串清空），iOS 侧现在补上了入口。
账号页在有昵称时**优先显示昵称**，手机号退到次要位置。

**鸿蒙侧要做**：设置页同样给一个昵称入口，调 `PATCH /me`。

### ⚪️ iOS 内部修复（鸿蒙不受影响，但值得知道是什么类型的坑）

- **正文编辑器不换行**：`TextEditor` 关掉滚动后会按无限宽排版，直接不折行。
  换成了原生会折行、会随内容长高的组件。
  → 鸿蒙端做多段落编辑器时，注意验证「自动折行 + 手动换行 + 随内容长高」三件事同时成立。
- **编辑日记时改动被静默丢弃**：编辑页写的是扁平文本字段，而渲染读的是块结构字段，
  两者不同步。→ 鸿蒙端如果也做「块结构 + 扁平文本冗余」的设计，
