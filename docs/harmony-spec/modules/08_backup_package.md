# 模块 · 备份包（`.memoir`）

> **iOS 状态**：导出 + 导入全链路已完成并验收（2026-08-06）。`formatVersion = 1` 已冻结。
> **格式权威**：[`Memoir/Docs/EXPORT_FORMAT.md`](../../EXPORT_FORMAT.md) —— 本文档讲**决策与陷阱**，
> 字段定义以那份为准，两边不一致时以那份为准。

---

## 为什么这是鸿蒙端最该先做的模块

**鸿蒙没有 CloudKit。** 用户从 iPhone 换到华为、或者想两台一起用，
备份包是**唯一**的数据通路。它不是"锦上添花的导出功能"，是双端战略的必要组件。

v1 鸿蒙端**只需要实现读取**（写入等鸿蒙侧功能完善后再做）。

## 一、容器：先判断是不是加密的

```
[ 未加密 ]  文件本身就是标准 ZIP，PK\x03\x04 开头
[ 已加密 ]  32 字节自定义头 + 密文，根本不是 zip
```

加密包的头部布局：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 8 | 魔数 `MEMOIRBK`（ASCII） |
| 8 | 1 | 版本 = 1 |
| 9 | 1 | 标志位，`0x01` = 已加密 |
| 10 | 16 | salt（明文，不敏感） |
| 26 | 12 | nonce（明文，AES-GCM 要求每次不同） |
| 38 | .. | 密文 + 尾部 16 字节认证标签 |

**解密**：`PBKDF2-HMAC-SHA256(密码, salt, 210000 轮) → 32 字节密钥`，再 `AES-256-GCM` 解开，
得到的才是 zip。

> **为什么不用 zip 自带的加密**：那套算法弱，且各平台实现不一致，跨端对不齐。
> 整体加密则两端只需要"派生密钥 + AES-GCM 解密"，都是标准库两行的事。

**只看魔数就能判断要不要问密码**，不必先尝试解密。加密与否 manifest 里也有
`encrypted` 字段，但**别依赖它**（那要先解开才读得到，鸡生蛋）。

## 二、⚠️ 解压后要往下找一层

iOS 端用系统的 `NSFileCoordinator` 打包，它会**把整个目录连目录名一起打进 zip**：

```
尺素备份_20260805/          ← 多出来的这一层
├── manifest.json
├── entries.json
├── letters.json
├── taxonomy.json
└── media/
```

而手工打的包或鸿蒙将来自己导出的包可能是**平的**（manifest 直接在顶层）。

**两种都要认**：先看顶层有没有 `manifest.json`，没有就扫下一层子目录。
不要靠目录名匹配 —— 中文目录名在 zip 里可能不带 UTF-8 标志位，解出来是乱码，
但**里面的文件名都是 ASCII**，所以扫描找 `manifest.json` 永远是可靠的。

（顺带：`__MACOSX` 这种 macOS 元数据目录要跳过。）

## 三、合并策略（**只有这一种，不要加别的**）

> **按 id 跳过已存在的，绝不覆盖。**

不提供"替换全部"。理由：那个功能一次误操作就能清空用户所有日记，
收益（少数用户想重置）远小于风险。真要重置，让他们删除重装。

**导入在任何情况下都只让库里的东西变多，不会变少。** 这条是对用户的承诺，请守住。

### 日记 / 来信：按 `id` 去重

### 标签与心情：**按「名字」去重，不按 id**

这条容易做错，专门说明：

`entries.json` 里的 `tags` 和 `mood` 存的是**名字字符串**，名字才是它们的真实身份。
而每台设备首启会各自生成一套默认标签和心情（id 各不相同）——
按 id 去重的话，用户导入一次就会多出一整套同名的「生活」「平静」，
用户看到的就是列表里重复了一遍。

### 来信关联日记：找不到的**静默丢弃**

`letters[].relatedEntryIDs` 里指向本地不存在的日记 id，忽略即可，不要阻断导入。

### 来信的 `status` / `triggerKind`：**原样存字符串，别过枚举**

后端会新增取值（例如 `triggerKind = "welcome"`）。
过一遍本端枚举的话，不认识的值会被抹成默认值，信息就丢了。

## 四、容错规则（比"正确"更重要）

这是用户**唯一的一份数据备份**，原则是**宁可残缺，也不要整包失败**：

| 情况 | 怎么办 |
|---|---|
| `formatVersion` 比自己支持的**大** | **拒绝导入**，提示"请先更新尺素"。不做半吊子解析 |
| 未知字段 | 忽略，不报错 |
| **已知字段缺失** | 用缺省值兜底，**不要整包拒收**。只有 `formatVersion` 必须可信（缺失按 1 处理） |
| 未知的块类型（`blocks[].type`） | 跳过该块，其余照常 |
| 媒体文件缺失 | 跳过该块，日记其余部分照常导入，**最后汇总告知**「N 张照片缺失」 |
| 某一条日记解析失败 | 只丢这一条，其余照常。**别让一条坏数据毁掉 499 条好的** |

> iOS 端的做法：整体解析失败时**退回逐条解析**，能救几条救几条。

## 五、Live Photo：静态图**绝不能重新编码**

Live Photo 的静态图里藏着一个 **content identifier**，系统靠它把静态图和视频配成一对。
**只要把图读进内存再编码一次（哪怕不改画质），这段元数据就没了**，配对永远失败，
而且失败是**静默的**（不报错，只是返回空）。

iOS 端因此出过两个用户可见的 bug：长按不播、以及**照片整个不显示**。

### `liveStill` 字段

尺素相机拍的照片会被居中裁成方形（相纸是方的），裁过的图配不了对。所以这类块带两份：

| 字段 | 是什么 | 干什么用 |
|---|---|---|
| `file` | 裁过的方图 | **显示** |
| `liveStill` | 未裁原图 | **配对** |
| `liveVideo` | 成对视频 | 播放 |

从相册选的 Live Photo 本来就没裁，只有 `file`，`liveStill` 缺席。

**读取规则**：`liveStill` 缺席时就用 `file` 去配对。

### 播放器必须有兜底

配对失败时**显示静态图，绝不能什么都不显示**。
退化成一张不会动的照片可以接受，凭空消失不行。

## 六、媒体落盘：重名不一定是同一张

包内媒体是扁平文件名。iOS 的照片名只取了 UUID 前 8 位，**跨库导入撞名并非不可能**。

处理：目标位置已存在同名文件时，
- **大小相同** → 视作同一份（多半是把自己的备份又导了一遍），复用，不重复占空间
- **大小不同** → **必须另起名字**并更新块内引用。
  否则这篇日记会指到别人的照片上，**比丢图还糟**

另外，json 里的文件名是**外部输入**，落盘前只取最后一段路径，
别让 `../../x` 这种决定往哪写。解压同理，要校验条目路径没跑出目标目录。

## 七、导入结果要告诉用户什么

```
新增日记 42 篇
跳过（已存在）6 篇
新增来信 3 封
新增日记本 2 个
⚠️ 有 1 张照片或录音在备份包里找不到，对应的日记其余内容已照常导入
```

导入前也要先让用户看清"这个包里有什么、什么时候导出的、来自哪台设备"，再决定导不导。
**导入只增不减，所以这一步不需要吓唬人**，只要说清"已有的会跳过"。

（导出那边则相反 —— 是把数据交出去，必须警告，且免责声明要勾选才能导出。）

## 八、鸿蒙端实现顺序建议

1. 解压 + 找包根 + 读 manifest + 判版本（**不含加密**，先跑通明文包）
2. 三个 json 的解析 + 容错
3. 按 id / 名字合并进本地库
4. 媒体落盘 + 缺失处理
5. 加密包解密（PBKDF2 + AES-GCM）
6. 导入前预览 + 导入结果 UI

第 1 步跑通就能验证"iOS 导的包鸿蒙能读"，这是这条链路上最值钱的一次验证，值得优先做。

> 🔴 **以后做导出时**（`10_BUILD_MANUAL.md` 6.5）：json 里的日期写成**不带毫秒**的 ISO8601（`2026-08-05T12:00:00Z`）。
> iOS 解析备份包用的解析器不认小数秒，直接写 `toISOString()` 的结果（带 `.123`）iOS 会导入失败。
> UUID 写大写；`manifest.platform` 写 `"harmony"`。验收标准是**鸿蒙导出的包在 iOS 真机上导入成功**。
