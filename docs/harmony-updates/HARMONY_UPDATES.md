## 规则

1. **文件名** `Uxx_<主题>.md`（如 `U01_world_penpals.md`），编号从 U01 往上排。不要用 `README.md` 这类通用名 ——
   `Memoir/` 是 Xcode 同步文件夹，重名文件会让打包失败
2. **基于谁**：每个更新包写明基于「v1」还是「v1 + U01…Uxx」。鸿蒙按顺序应用，不跳号。
   **例外**（2026-10-22 起）：包头写明「内容只依赖 v1」的，前面的包还没交付也能先做 —— 世界笔友（U01）要等 iOS 做完，排在它后面又不依赖它的包不必干等
3. **交付即冻结**：交付后发现写错了，也不改它，在下一个更新包里写「更正 Uxx 的某节」
4. **v1 的规则编号不复用**：
   - 新规则接着各组往下编（`R-POST-13`、`R-POST-14`…），或开新组（如 `R-PENPAL-01`）
   - 改了 v1 的某条：写「**取代 R-POST-07**」，给出完整的新规则文字，不要只写差异
   - 撤销 v1 的某条：写「**作废 R-XXX-NN**」并说明为什么、鸿蒙已经做了的话要怎么拆
5. **交付方式**：鸿蒙仓库新建 `docs/harmony-updates/`，把更新包原样拷进去；`docs/harmony-spec/`（v1 副本）不动
6. **鸿蒙一边做 v1、一边做已交付的包**（2026-10-22 起）：每个包的「改了什么」写了它取代 / 补充 v1 的哪几条，「鸿蒙已经做了的部分怎么改」写了对到 v1 的哪一步。
   v1 那一步**还没做**的，做 v1 卡时直接按更新包的新规则做（两张卡一起做，别先照 v1 做一遍再拆）；**已经做完**的，单独做一次更新包的卡来改。agent 的做法写在鸿蒙仓库的 `TASK.md`

## 一个更新包里写什么

```markdown
# Uxx · <主题>

> 基于：v1（+ U01 …）｜ 状态：草稿 / 已交付 yyyy-mm-dd

## 一句话
## 改了什么、为什么
## 规则（新增 / 取代 / 作废，带编号）
## 数据模型变化（字段、默认值、迁移；对照 v1 的 05_DATA_MODEL.md 写差异）
## 后端接口变化（对照 v1 的 02_BACKEND_API.md）
## 备份包变化（升不升 formatVersion）
## 七种语言的新文案（取自 iOS 的 xcstrings）
## 任务卡（格式同 v1 手册：目标 / 先读 / 要做 / 不要 / 验收，编号 Uxx-1、Uxx-2…）
## 鸿蒙已经做了的部分怎么改（拆什么、迁移什么）
```

鸿蒙那边的 agent 用法不变：`TASK.md` 里加一句「更新包的任务卡在 `docs/harmony-updates/`」，交付第一个更新包时一起改。
